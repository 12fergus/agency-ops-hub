# Decisions (ADRs)

## ADR-001 — Product assumptions (approved 2026-11-20)

One agency, not SaaS/multi-tenant; 3–20 employees using browsers on the office LAN; one always-on office PC hosts the app; the administrator runs backups; no external API integrations in the MVP; no real client data seeded in development.

## ADR-002 — Stack and pinned versions (2026-11-20)

Node 26 (current LTS line on the dev host), pnpm 12.21.0, TypeScript **6.0.3** (not 7.x: `typescript-eslint` 8.73 supports `<6.1`), Fastify 5.12, `@fastify/static` 10.1 (serves the SPA, required by the same-origin design), Drizzle ORM 0.45 + better-sqlite3 13.2 (SQLite 3.54), Zod 4.6, React 19.3, Vite 8.3, Tailwind 4.3, TanStack Query 5.108, Vitest 5.1, Testing Library, Playwright 1.65, ESLint 10 + Prettier 3.10. All versions are exact in `package.json`; the lockfile pins transitive versions.

Installed later, when their phase needs them: argon2, TanStack Table, React Hook Form + resolvers, drizzle-kit, shadcn/ui primitives, Fastify cookie/helmet/rate-limit plugins, and a client-side router (not named in the spec; to be approved in Phase 1).

## ADR-003 — Repository layout (2026-11-20)

The monorepo lives at the repo root (`C:\dev\test`), not in an `agency-crm/` subfolder. `@agency-crm/shared` is consumed from `src` in dev/tests and from `dist` in production builds, so no watch-build step is needed in development.

## ADR-004 — Fonts (2026-11-20)

Use system fonts with Hebrew coverage (Segoe UI / Arial). No Google Fonts or other external requests: the LAN may be offline, and the CSP can stay `self`-only.

## ADR-005 — IDs and timestamps (2026-11-20, Phase 1)

IDs are UUIDv7, generated by a 10-line in-house helper (`apps/api/src/lib/ids.ts`, RFC 9562 layout, `crypto.randomBytes`). No `uuidv7` dependency. Timestamps are UTC ISO-8601 text with milliseconds. A DB default produces the same format as `toISOString()`, so values from the DB and from the app sort and compare consistently as strings.

## ADR-006 — Case-insensitive email without COLLATE NOCASE (2026-11-20, Phase 1)

The spec asked for `email UNIQUE COLLATE NOCASE`. Instead, emails are stored normalized (trim + lowercase) and protected by a `CHECK (email = lower(trim(email)))` plus a plain unique index. Same guarantee, and every equality lookup uses the index without collation surprises. SQLite's `lower()` only folds ASCII. Non-ASCII emails are rare and are folded by JS before insert.

## ADR-007 — Same-client invariants in the database (2026-11-20, Phase 1)

Parent tables expose `UNIQUE (id, client_id)` (or `(id, pipeline_id)`), and children reference them with **composite foreign keys**. A lead therefore cannot point at another client's pipeline, stage, campaign or import batch, and a task cannot point at another client's lead, even through raw SQL. Services check the same rules first and return `CROSS_CLIENT_REFERENCE` (422). Assignee access isn't a DB rule because admins access every client without a membership row.

## ADR-008 — No cascading deletes (2026-11-20, Phase 1)

All FKs use the default `NO ACTION`. Deleting a client or user that still has history fails. Records are archived (`archived_at`) or disabled (`is_active = 0`). Hard deletion and retention purges will be explicit admin maintenance operations.

## ADR-009 — Schema additions beyond the spec (2026-11-20, Phase 1)

- `leads.consent_status` (`unknown|granted|denied`) + `consent_at`: the spec's privacy section requires consent tracking on imported leads.
- `leads.import_batch_id`: links CSV-imported leads to their batch (undo/traceability), constrained to the same client.
- `client_members.created_at`, `lead_activities.created_at`: when a row was recorded, as distinct from `occurred_at`.
- Enum CHECKs for `leads.source`, `campaigns.channel`, etc. `ingestion_events` is deferred to the webhook phase.

## ADR-010 — Migrations, transactions and demo data (2026-11-20, Phase 1)

- `db:migrate` uses Drizzle's migrator: all pending migrations run in one transaction. It backs up an existing DB before applying anything. It never runs automatically on server start, so the admin controls when the schema changes.
- `withTransaction` uses `BEGIN IMMEDIATE` (avoids `SQLITE_BUSY` on lock upgrade in WAL) and nested savepoints. Callbacks must be synchronous, which is enforced at runtime.
- Demo seed: a separate command that requires `--confirm-demo`. It is refused in production and on any DB with users or clients. Users get an unusable password hash. Emails use the `.test` TLD. Phone numbers are invented and must never be dialled.
- Backups: SQLite online backup API, converted to a single file (`journal_mode=DELETE`), then `integrity_check`.

## ADR-011 — Phase 1 review outcomes (2026-11-20)

The code review found no blockers. Fixed in this phase: migration drift/hash detection, stricter seed guards, quarantine of failed backups, client-scoped `updateLead`, archived-lead checks, a service-level import-batch check, PII-free audit snapshots for leads and tasks, UTC timestamp CHECKs (so `0000_init` was regenerated before it was ever applied to a real DB), pragma order and WAL verification, phone edge cases, and Win32 long paths.
Deferred to Phase 2 (auth), because they need an authenticated actor: lookups scoped to the actor (`findLeadForActor`), NOT_FOUND instead of CROSS_CLIENT_REFERENCE for IDs the actor can't access, and a DB error mapper for constraint violations (raw SQLite errors become 409/422 envelopes).
Accepted, documented only: `db:migrate` doesn't lock out a running server (the procedure requires stopping it), and `foreign_key_check` runs after commit.

## ADR-012 — Authentication and authorization design (2026-11-21, Phase 2)

- **No new dependencies.** Argon2id comes from Node's built-in `crypto.argon2` (Node ≥ 24.7). The app handles only one fixed cookie with a base64url value, so a tiny tested module (`lib/cookies.ts`) replaces `@fastify/cookie`. Rate limiting is an in-memory fixed window, which is adequate for one API process. The web app uses a 15-line hash router.
- **Opaque server-side sessions, not JWTs.** Logout, disabling and role changes must take effect immediately, so the session lives in SQLite and the cookie carries only a random token. A database leak exposes only hashes.
- **The user is checked on every request.** `authenticate` joins the session with the user and rejects inactive users, so disabling is immediate even if session revocation were missed.
- **A privilege change forces a new login.** Changing a role revokes all of that user's sessions.
- **404 when there is no access.** A non-member gets `NOT_FOUND`, identical to a non-existent id, so IDs can't be probed. `403 FORBIDDEN` is used only when the resource is visible but the action isn't allowed (e.g. an employee managing members).
- **Who controls membership.** Only admins and the client's **owner** managers can change membership. Managers may add employees or managers as `collaborator` and remove collaborators. They can never grant `owner`, add admins, or remove owners. Admins can do everything and assign ownership.
- **Admin lockout protection.** Admins can't disable themselves or change their own role, and the last active admin can't be demoted or disabled.
- **CSRF.** Defence in depth: SameSite=Lax, an Origin/Referer same-host check on every state-changing request (including login), and JSON-only bodies. With these checks a same-origin JSON API needs no CSRF token. `TRUSTED_ORIGINS` covers a reverse-proxy hostname that differs from `Host`.
- **Secure cookie flag.** `COOKIE_SECURE=auto` sets Secure when the request arrived over HTTPS; behind a TLS-terminating proxy, set `TRUST_PROXY=true`. No `__Host-` prefix yet, because the office LAN may start on plain HTTP. Revisit once TLS is mandatory.
- **First admin.** Created only by the host CLI: interactive (TTY), hidden password typed twice, refused once an active admin exists. There is no HTTP bootstrap route, so "the first visitor becomes admin" can't happen.
- **Unknown API routes return 401 when unauthenticated**, because the default-deny hook runs before the 404 handler.

## ADR-013 — Phase 2 review outcomes (2026-11-21)

The code review found no blockers. Fixed:

- **The security hook decides on the router's view.** It now checks the matched route pattern, or the percent-decoded path for 404s, instead of `req.url`. Before, `/%61pi/v1/...` reached API handlers while skipping the Origin check and default-deny. Each handler's own `actorOf()` still blocked reads, but a forged cross-origin logout succeeded. A regression test covers it.
- **Login counters are incremented before the async password check**, so parallel guesses can't exceed 5 per account.
- **`trustProxy: 'loopback'`** instead of `true`, so client-forged `X-Forwarded-For` can't rotate the per-IP limiter key.
- **The rate limiter's memory is hard-capped** (expired entries go first, then the oldest).
- **Nits fixed:**
  - accounts with placeholder hashes now go through the dummy Argon2 run (no timing oracle);
  - login re-checks the user inside the transaction (disabled or password changed mid-login → no session);
  - 5xx responses always use code `INTERNAL`;
  - the CLI swallows arrow-key escape sequences and no longer prints the email.

Accepted:

- A lockout on one account can affect its real owner (documented in operations.md).
- Admins may leave a client with no owner, so only admins can manage its members.
- Concurrent first-admin bootstraps could create two admins, which is negligible for a host-only CLI.
- `Origin` is compared to `Host`; a proxy that rewrites Host needs `TRUSTED_ORIGINS`.
- No `__Host-` cookie prefix until HTTPS is mandatory.

## ADR-014 — Password policy: 8+ with letter, digit and symbol (2026-11-21)

The user asked for 6 characters with special symbols. We agreed on **8–256 characters with at least one letter (any script, Hebrew included), one digit and one symbol**, no leading or trailing space, and not containing the email's name part.

- Six characters is below every mainstream minimum. Current NIST/OWASP guidance prefers length over composition rules, so 8 + composition is a compromise, accepted given the login rate limit and Argon2id.
- The rules live in one place (`packages/shared/src/password-policy.ts`). The API enforces them and the web form shows the same checklist live, so the two cannot disagree. The API answers `422 VALIDATION` with the specific rule code; the UI maps it to Hebrew.
- The policy applies when a password is set. Existing passwords, such as the first admin's, keep working.
- Deferred (progress.md items 7–8): email codes (2FA or one-time verification) and Google sign-in. Both are external integrations that need provider decisions, internet access and, for Google, HTTPS on a real domain.

## ADR-015 — Self-signup with admin approval (2026-11-21)

The user asked for a sign-up button on the login page. Because anyone on the office LAN can open that page, sign-ups are **pending until an admin approves them**:

- A sign-up creates `role=employee, is_active=0, approved_at=NULL`. It can't log in, and login gives the same generic error as a wrong password. It also has no client memberships, so after approval it still sees no client data until it is assigned.
- **Approval** = `POST /users/:id/enable`, which sets `approved_at` and activates the account. `status` is derived: active / pending (inactive and never approved) / disabled (inactive and approved before).
- **No enumeration:** signing up with an existing email returns the same 202 and changes nothing. A password hash is computed either way, so timing matches.
- Rate limit: 5 sign-ups per IP per hour. `SELF_SIGNUP=false` hides the button and makes the route 404. `GET /auth/options` tells the UI.
- **Migration 0001** adds `users.approved_at` as a plain nullable column and backfills existing users as approved. It has no CHECK constraint on purpose: in SQLite, adding a CHECK means rebuilding `users`, which every table references, and with FKs enforced inside the migration transaction that rebuild would fail (see operations.md → Schema changes). The format is guaranteed by the app (`nowIso()`).
- The public-route test now pins the exact list of public routes, so making a route public needs a deliberate test change.

## ADR-016 — Sign-up logs in immediately (approval optional) (2026-11-21)

The user asked that sign-up lead straight to the main screen instead of a "pending approval" message, which supersedes the default in ADR-015.

- **Default (`SIGNUP_REQUIRES_APPROVAL=false`):** a sign-up creates an active, approved **employee with no client memberships** and starts a session in the same transaction (the same `startSession` as login: fresh token, audited as `auth.signup_login`). Authorization is membership-based, so the new user sees no client or lead data and no admin pages until an admin assigns them.
- **Accepted trade-offs:**
  - Anyone on the LAN can create an account; it is rate-limited, and unwanted accounts can be disabled.
  - An already-registered email now gets `409 EMAIL_TAKEN`, because we can't log the person in as someone else. That reveals the email exists, which is accepted for an internal tool. Hashing still runs in every case.
- **Approval mode (`SIGNUP_REQUIRES_APPROVAL=true`)** keeps the ADR-015 behaviour: pending, no session, identical answer for existing emails.
- **Risk to watch:** any future feature that shows data to "any logged-in user" (not scoped by client membership) would expose it to self-signups. Every data route must keep going through `authorizeClientAccess`.

## ADR-017 — First admin without a terminal (2026-11-21)

In production the office PC may run the CRM as a service, with nobody using a shell, so `pnpm auth:create-admin` alone isn't enough. Added (the CLI stays for developers and recovery):

1. **Setup page + one-time code (default).** While the DB is migrated and has no login-capable admin, the server generates a 12-character code (about 59 bits, unambiguous alphabet). It writes the code to `setup-code.txt` next to the database; **the log only names the file, never the code** (no secrets in logs). `GET /setup/status` makes the web show **הגדרה ראשונית** instead of login. `POST /setup` needs the code (hashed, constant-time compare, 10 tries per IP per 15 min), creates the admin through the same `bootstrapFirstAdmin` (which re-checks "no admin", so concurrent attempts can't both succeed) and logs them in. The file and code are then deleted and the routes answer 404. Trust model: whoever can read the server's data folder is the owner. A visitor on the LAN can't take over a fresh install, which is what makes this safer than "the first visitor becomes admin".
2. **`INITIAL_ADMIN_EMAIL` / `INITIAL_ADMIN_PASSWORD` / `INITIAL_ADMIN_NAME`** for scripted installs: applied once at startup while no admin exists, ignored (with a warning) afterwards. An invalid value is logged (rule code only) and setup falls back to the code page instead of crashing the service. The password sits in plain text in the config, so the docs tell the operator to remove it after first start.

Open point: migrations still need `pnpm db:migrate`. A no-terminal production install would also need an opt-in "migrate on startup" (with the automatic pre-migrate backup), which ADR-010 deliberately excluded. To be decided with the deployment/operations phase.

## ADR-018 — Clients module rules (2026-11-21, Phase 3)

- **Who may do what:**
  - **Admins** create clients and can do everything.
  - **Owner-managers** edit their client's details and contacts, and add or remove collaborators.
  - **Collaborators and employees** read only.
  - **Archive/unarchive** is admin-only.
  - Non-members get 404 everywhere.
  - Each client response carries the actor's `permissions` (computed by the same rules), so the UI shows exactly what the server allows. The server still re-checks every call.
- **Archive, not delete:** archiving sets `status='archived'` + `archived_at` and keeps all members, contacts, leads and history. Archived clients drop out of the default list (`status=current`) and are read-only (409) until unarchived. There is no client DELETE route.
- **Contacts may be deleted:** they are reference data without history; audit records the deletion (without contact PII).
- **PATCH schemas have no defaults.** Zod keeps a field's `.default()` through `.partial()`, so a PATCH schema derived from the create schema silently reset omitted fields (a paused client back to active, a primary contact to non-primary). Field rules now live in a defaults-free base; create adds defaults, PATCH uses `.partial()` of the base. A regression test covers it.
- **Listing:** scoping is part of the SQL (`IN (memberships)`), never a post-filter, so totals and pages are correct. Sort only via an allowlist map. Search uses `LIKE … ESCAPE` with escaped user wildcards. Page size is at most 100.
- **TanStack Table v9** (`@tanstack/react-table` 9.3.1, named in the spec): `useTable` with `rowSortingFeature` + `rowPaginationFeature`, `manualSorting`/`manualPagination` (the server owns both), and controlled state in React. Query data goes straight into the table with no copy into state.
- **UI patterns:** an accessible drawer (dialog, focus moves to the first field and returns to the opener, focus trap, Escape), in-page confirmations instead of `window.confirm` (browser dialogs also break automated checks), and hash routes `#/clients` and `#/clients/<id>`.

**Phase 3 review outcomes (2026-11-21):**

- **Fixed (blocker):** staff add/remove on an **archived** client was still accepted, contradicting `canManageStaff:false`. Every write path (details, contacts, staff) now refuses archived clients with 409. A regression test covers all six write routes for admin and owner.
- **Fixed:**
  - the drawer focus effect re-ran on parent re-renders and stole focus mid-typing (`onClose` is now kept in a ref);
  - the list snaps back when the current page is past the last one;
  - inline confirmations support Escape, return focus to their trigger, and name their target in the Yes/No labels;
  - "page X of Y" is one translated sentence;
  - phone search ignores formatting (`0501234567` finds `050-123-4567`);
  - ids are URL-encoded in API paths;
  - a duplicate staff query was removed.
- **Accepted (by design):**
  - **Unarchive restores the lifecycle to `active`.** Since ADR-019 the business status (`status_id`, e.g. מושהה) is separate and **is kept** through archive and unarchive; only the archived flag changes. The audit log records the before and after.
  - **Admins may remove a client's last owner.** The client then has no owner-manager, so only admins can edit it until a new owner is assigned.
  - **The count and the page are read in two statements, outside a transaction.** Under concurrent writes the total can be off by one for a moment, which is acceptable for a list view.

## ADR-019 — Custom client statuses, workers edit/create, client photos (2026-11-21, Phase 3)

Requested by the user during Phase 3:

- **Statuses are admin-defined** (`client_statuses`: name, palette color, position, one default). Every client has one (`clients.status_id`); new clients get the default. Lists filter by it and sort by the admin's order (`position`). The old `clients.status` column now only marks the **lifecycle** (archived or not), and its existing CHECK constraints still hold. Former "paused" clients became the מושהה status in migration 0002 (additive columns plus a backfill, with no table rebuild). Colors are a fixed palette mapped to vetted classes, never free CSS. The UI always shows the status name, so color is never the only cue.
- **Statuses in use, or the default status, can't be deleted**, so every client always has a valid status.
- **Workers:**
  - **Any role may create a client.** A non-admin creator is assigned automatically: managers as **owner**, employees as collaborator.
  - **Any assigned member may edit** details, status, contacts and photo.
  - Staff management (admins and owner-managers) and archive (admins) are unchanged.
  - Risk accepted with ADR-016's instant sign-up: anyone on the LAN can create clients. They only ever see their own, and admins see everything and can archive.
- **Photos:**
  - **Upload:** `@fastify/multipart` (approved dependency) with hard limits (1 file, 2 MB, no extra fields or parts).
  - **Type check:** by magic bytes (PNG, JPEG, WebP only; SVG is rejected because it is scriptable).
  - **Storage:** `<UPLOADS_DIR>/clients/<clientId>.<ext>`, written to a temp file and then renamed.
  - **Serving:** through an authorized route with the sniffed MIME type, `nosniff` and `no-store`.
  - **Open point:** `db:backup` doesn't include uploads yet (operations.md). Combine them in the Operations phase.
- **Browser-check fix:** a 401 during use removed the first-run-setup query, so the app hung on "טוען…". App-state queries (`auth`, `setup`) now survive cache clears, with a regression test.

**ADR-019 review outcomes (2026-11-21):** no blockers.

- **Photo save order:** temp file, then the DB commit, then the file swap. A failed DB update now keeps the current photo and leaves no temp file; tested with a simulated failure.
- **Status counts are admin-only.** For everyone else `clientCount` is null, since the counts span clients they can't see.
- **Versioned photo URLs** may be cached privately for 1 day; all other API responses stay `no-store`.
- **Smaller fixes:** docs and comments brought up to date (schema, multipart CSRF note); the avatar retries after a new upload; status counts refresh after client changes; a failed reorder reloads the list; a 0002 backfill test was added.

## ADR-020 — Communication log and follow-up tasks (2026-11-21, Phase 4)

- **Communication records are history.** Any member or admin may add one. Only the **author or an admin** may edit it, and nobody deletes it. A record keeps its author, and its `summary` is free text about real people, so the summary stays **out of the audit log**; only the type, time and contact id are recorded. Deleting a contact clears it from the records instead of blocking the delete.
- **"צור משימת המשך"** is an ordinary task with `communication_id`. A composite FK guarantees the same client in the DB, and the service returns a field error (422) for a record of another client, so nobody can probe ids. Tasks are listed on their record, and each task shows "נוצרה מתוך".
- **Task statuses are fixed:** `open → in_progress → done`, plus `cancelled` (chosen by the user). Overdue = a deadline in the past while `open` / `in_progress`, computed by the server at read time. Tasks are never deleted: cancel instead.
- **Who may assign:** any member of the client (or an admin) may create or edit tasks and assign them to **anyone with access to that client**, e.g. a campaign manager assigning a designer (chosen by the user). The assignee is validated on the server on every create and reassign.
- **Visibility:**
  - Non-admins see only tasks of clients they are members of, including tasks assigned to them. If someone is removed from a client, its tasks disappear from their queue and stay with the client; reassign them from the client page.
  - Archived clients' tasks stay readable but leave the active queue and are read-only (409).
- **Times:** forms enter Israel time (Asia/Jerusalem) whatever the computer's own time zone is (`lib/datetime.ts`, tested for summer and winter time). Times are stored as UTC.
- **Migration 0003:** drizzle-kit generated a table rebuild that copied the two _new_ columns from the old table, which would have failed. This was fixed by hand **before the first apply** (copy NULL), and a test proves existing tasks survive.

**ADR-020 review outcomes (2026-11-21):** no blockers.

- **Assignee check:** only a _change_ of assignee is validated, so a task whose assignee was deactivated can still be edited. Tested.
- **Archived clients:** their tasks are never flagged overdue. Follow-up tasks inside a record now show their overdue state. Archived = read-only (409) remains intentional.
- **Accessible names:** record buttons include the author, so they stay unique even for two records of the same type in the same minute.
- **Deferred:**
  - no upper bound on future `occurredAt`;
  - when someone is removed from a client, their tasks aren't reassigned automatically (documented above).

**Phase 4 browser-check outcomes (2026-11-21):**

- **Archiving now refreshes the communication and task views,** so they become read-only right away instead of after a reload. Covered by e2e.
- **A client's own task section** keeps showing its tasks after archiving (read-only). Only the personal "active" queue hides archived clients. Tested.
- **"נוצרה מתוך"** isolates the date as left-to-right inside the Hebrew sentence.
- **Not reproduced:** two session drops seen while one Chrome profile switched between test accounts. Logging in as another user ends the previous session by design, and logging out clears the shared cookie; no code path revokes sessions otherwise.
