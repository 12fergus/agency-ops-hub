# Decisions (ADRs)

## ADR-001 — Product assumptions (approved 2026-11-20)

One agency, not SaaS/multi-tenant; 3–20 employees using browsers on the office LAN; one always-on office PC hosts the app; the administrator runs backups; no external API integrations in the MVP; no real client data seeded in development.

## ADR-002 — Stack and pinned versions (2026-11-20)

Node 26 (current LTS line on the dev host), pnpm 12.21.0, TypeScript **6.0.3** (not 7.x: `typescript-eslint` 8.73 supports `<6.1`), Fastify 5.12, `@fastify/static` 10.1 (serves the SPA, required by the same-origin design), Drizzle ORM 0.45 + better-sqlite3 13.2 (SQLite 3.54), Zod 4.6, React 19.3, Vite 8.3, Tailwind 4.3, TanStack Query 5.108, Vitest 5.1, Testing Library, Playwright 1.65, ESLint 10 + Prettier 3.10. All versions are exact in `package.json`; the lockfile pins transitive versions.

Installed later, when their phase needs them: argon2, TanStack Table, React Hook Form + resolvers, drizzle-kit, shadcn/ui primitives, Fastify cookie/helmet/rate-limit plugins, and a client-side router (not named in the spec; to be approved in Phase 1).

## ADR-003 — Repository layout (2026-11-20)

The monorepo lives at the repo root (`C:\dev\test`), not in an `agency-crm/` subfolder. `@agency-crm/shared` is consumed from `src` in dev/tests and from `dist` in production builds, so no watch-build step is needed in development.

## ADR-004 — Fonts (2026-11-20)

Use system fonts with Hebrew coverage (Segoe UI / Arial). No Google Fonts or other external requests: the LAN may be offline, and the CSP can stay `self`-only.

## ADR-005 — IDs and timestamps (2026-11-20, Phase 1)

IDs are UUIDv7, generated by a 10-line in-house helper (`apps/api/src/lib/ids.ts`, RFC 9562 layout, `crypto.randomBytes`). No `uuidv7` dependency. Timestamps are UTC ISO-8601 text with milliseconds. A DB default produces the same format as `toISOString()`, so values from the DB and from the app sort and compare consistently as strings.

## ADR-006 — Case-insensitive email without COLLATE NOCASE (2026-11-20, Phase 1)

The spec asked for `email UNIQUE COLLATE NOCASE`. Instead, emails are stored normalized (trim + lowercase) and protected by a `CHECK (email = lower(trim(email)))` plus a plain unique index. Same guarantee, and every equality lookup uses the index without collation surprises. SQLite's `lower()` only folds ASCII. Non-ASCII emails are rare and are folded by JS before insert.

## ADR-007 — Same-client invariants in the database (2026-11-20, Phase 1)

Parent tables expose `UNIQUE (id, client_id)` (or `(id, pipeline_id)`), and children reference them with **composite foreign keys**. A lead therefore cannot point at another client's pipeline, stage, campaign or import batch, and a task cannot point at another client's lead, even through raw SQL. Services check the same rules first and return `CROSS_CLIENT_REFERENCE` (422). Assignee access isn't a DB rule because admins access every client without a membership row.

## ADR-008 — No cascading deletes (2026-11-20, Phase 1)

All FKs use the default `NO ACTION`. Deleting a client or user that still has history fails. Records are archived (`archived_at`) or disabled (`is_active = 0`). Hard deletion and retention purges will be explicit admin maintenance operations.

## ADR-009 — Schema additions beyond the spec (2026-11-20, Phase 1)

- `leads.consent_status` (`unknown|granted|denied`) + `consent_at`: the spec's privacy section requires consent tracking on imported leads.
- `leads.import_batch_id`: links CSV-imported leads to their batch (undo/traceability), constrained to the same client.
- `client_members.created_at`, `lead_activities.created_at`: when a row was recorded, as distinct from `occurred_at`.
- Enum CHECKs for `leads.source`, `campaigns.channel`, etc. `ingestion_events` is deferred to the webhook phase.

## ADR-010 — Migrations, transactions and demo data (2026-11-20, Phase 1)

- `db:migrate` uses Drizzle's migrator: all pending migrations run in one transaction. It backs up an existing DB before applying anything. It never runs automatically on server start, so the admin controls when the schema changes.
- `withTransaction` uses `BEGIN IMMEDIATE` (avoids `SQLITE_BUSY` on lock upgrade in WAL) and nested savepoints. Callbacks must be synchronous, which is enforced at runtime.
- Demo seed: a separate command that requires `--confirm-demo`. It is refused in production and on any DB with users or clients. Users get an unusable password hash. Emails use the `.test` TLD. Phone numbers are invented and must never be dialled.
- Backups: SQLite online backup API, converted to a single file (`journal_mode=DELETE`), then `integrity_check`.

## ADR-011 — Phase 1 review outcomes (2026-11-20)

The code review found no blockers. Fixed in this phase: migration drift/hash detection, stricter seed guards, quarantine of failed backups, client-scoped `updateLead`, archived-lead checks, a service-level import-batch check, PII-free audit snapshots for leads and tasks, UTC timestamp CHECKs (so `0000_init` was regenerated before it was ever applied to a real DB), pragma order and WAL verification, phone edge cases, and Win32 long paths.
Deferred to Phase 2 (auth), because they need an authenticated actor: lookups scoped to the actor (`findLeadForActor`), NOT_FOUND instead of CROSS_CLIENT_REFERENCE for IDs the actor can't access, and a DB error mapper for constraint violations (raw SQLite errors become 409/422 envelopes).
Accepted, documented only: `db:migrate` doesn't lock out a running server (the procedure requires stopping it), and `foreign_key_check` runs after commit.
